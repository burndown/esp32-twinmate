# 2026-10-12 到 10-20 的改动

这是一份更新记录，地址和域名都用占位符。固件改动在 `firmware/muse-cloud.patch`（基于上游 `fa07304`），网关在 `worker/`，家里这一侧的服务在 `home/`。

## 固件（Waveshare ESP32-S3-Touch-AMOLED-1.75C）

- **`display.show_text`**：让 Muse 把文字直接发到圆屏。黑底白字，超过一屏逐行向上滚，手指可拖，点一下关闭，约 4000 字节；默认同时朗读（`speak:false` 只显示），滚动跟着朗读进度。
- **所有消息（推送）**：设置 → Sound → All messages（默认关）。Muse 在没有回合等待它时发来的消息会唤醒屏幕并念出来；只对主对话有效，线程会话只收到摘要。
- **冻屏修复**：应用了上游 PR #34（`muse_lcd_bands.c`）。1.75C 上只验证了能运行，没有长时间待机的数据。
- **眼睛头像**：设置 → Sound → Eyes（默认开）。两只眼睛，表情跟着 Muse 状态变，说话时随声音起伏；单击开心、双击惊讶、长按生气、拖动眼神跟手、上滑惊讶、下滑困倦；倾斜板子转眼神，用力摇 4 下发晕（QMI8658）。改编自 [zongzhu-bot](https://github.com/Liu-zhongxian/zongzhu-bot)（MIT）。
- **干净主屏**：状态图标、状态文字、喇叭按钮和按键提示平时隐藏，碰一下淡入，4 秒后淡出，隐藏期间点不到。
- **等待计时圈**：松手开始计时，周围的圈 60 秒画满；等待期间回到"思考"状态，答案念出来时清零。
- **出门（连着别的 Wi-Fi）**：按 Wi-Fi 名选地址（`MUSE_HOME_SSID`）；不等 Muse，请求带 `away` 让网关直接回答；Muse 的后台重连（VM 会话、令牌刷新、Noise 会话、聊天会话）暂停。
- **两个读写修复**：①ESP-IDF 的 `esp_http_client_read` 会一直等到缓冲区读满，短确认话后面跟着长时间空白时会被卡住，固件改成逐字节读；②网关故意回 503（让设备去问 Muse）时，不再把它当成失败去重试备用地址（每轮白花约 2 秒）。

## 网关与家里这一侧

- **大模型**：除了阿里云、火山、DeepSeek、自定义，新增"Responses 接口"（兼容 OpenAI Responses，可带 `web_search`）。用 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI) 接订阅账号时，Gemini 在"自定义"里加 `{"tools":[{"google_search":{}}]}`，实测 2 到 3 秒答对；GPT 走 Responses 接口，约 17 秒，因为先搜索后写。这是把订阅账号经非官方代理当 API 用，可能违反服务条款，自行评估。
- **系统提示**：带当天日期，要求"今年、最新"先搜索；回复里的 `* # \`` 会被去掉。
- **公网入口**：路由器端口转发到一个只放行 `POST /chat /tts /stt /bot-reply` 的 HTTPS 转发服务（`home/gw-proxy.mjs`，限速，错误令牌封禁，记耗时日志），证书用 acme.sh 的 DNS 验证。运营商通常封 80/443，所以用 DNS 验证和高位端口。
- **Webhook 机器人**（比如 Grok Bot）：出门时每一轮交给它；先让设备念确认话，再发 Webhook，机器人把答案 `POST` 回 `/bot-reply/<id>/<令牌>`（一次性令牌，在路径里，避开 `&amp;` 转义）；Webhook 发不出去时同一条回复里改由普通大模型作答。可选经一台有公网 IP 的中转服务器（SSH 反向隧道 + nginx，见 `home/bot-tunnel.service`、`home/relay-nginx.conf`），回调走标准 443，隧道断了自动直连。

## 踩过的坑

- nginx 反向代理默认用 HTTP/1.0，有的机器人的服务器会回 `426 Upgrade Required`，要加 `proxy_http_version 1.1`。
- Webhook 路径是机密，中转站点要关掉访问日志。
- 用 `sed -i` 改日志文件会让 nginx 继续写已删除的旧文件，要 `nginx -s reopen`。
- 转发服务的白名单必须包含机器人回调的路径，否则回调会被拒成 404。

## 2026-10-21：WireGuard 隧道和可换主页形象

见 README「固件」里的两条。要点：隧道用 `esphome/wireguard`，ESP-IDF 6.0.1 上有三个坑，补丁里已处理：

- `esp_netif` 的回调把 lwIP 网卡的 `state` 当成自己的指针，隧道网卡加进去时崩溃（`LoadProhibited`）。要打开 `CONFIG_ESP_NETIF_BRIDGE_EN=y`，这样 esp_netif 把指针放在 client data 里。
- 组件默认每个对端只允许 1 个地址，`0.0.0.0/0` 加不进去，数据包报"no peer"被丢。补丁在 `components/muse/CMakeLists.txt` 里给它定义 `CONFIG_WIREGUARD_MAX_SRC_IPS=2`。
- 路由器的 DNS 可能返回假地址（本机实测 `198.19.0.x`），在隧道里不通，所以隧道起来时改用隧道里的公共 DNS 并清掉 lwIP 的 DNS 缓存。

另外：组件调用 lwIP 原始接口，需要持有 `LOCK_TCPIP_CORE()`；握手要用系统时钟，没校时时先用 NTP。

### 同日补充：Answers 菜单和内存

- 设置 → Answers 选谁来回答（Muse / Grok Bot / Gemini），在家在外都生效；WireGuard 的 Auto 只在选 Muse 时才起隧道。网关 `POST /chat` 新增 `gemini: true`。
- 去网关的请求（识别、对话、语音）用 `esp_http_client_config_t.if_name` 绑在 Wi-Fi 网卡上，不进隧道；连 Muse 的连接不绑。
- 内部 RAM 很紧：每轮的网络任务（识别、对话、取语音）和 WireGuard 管理任务的栈用 `xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)` 放进 PSRAM，结束时 `vTaskDeleteWithCaps(NULL)`。这些任务里不能写闪存。不这样做，选 Muse 时的长回复会在第十几段语音时因为取语音失败而停下。
