## Firmware (Waveshare ESP32-S3-Touch-AMOLED-1.75C)

- **`display.show_text`.** Lets Muse send text straight to the round screen: white on black, scrolling up line by line when longer than a screen, draggable with a finger, a tap closes it, about 4,000 bytes. By default it is also read aloud (`speak:false` only shows it), and the scrolling follows the speech.
- **All messages (push).** Settings → Sound → All messages (off by default). A message Muse sends while no turn is waiting for it wakes the screen and is spoken; it works only for the main conversation, and thread conversations get only a summary.
- **Screen freeze fix.** Upstream PR #34 (`muse_lcd_bands.c`) was applied. On the 1.75C I verified only that it runs; I have no data from a long standby.
- **Eyes avatar.** Settings → Sound → Eyes (on by default). Two eyes whose expression follows Muse's state and which move with the loudness while speaking; tap — happy, double tap — surprised, long press — angry, drag — the gaze follows your finger, swipe up — surprised, swipe down — sleepy; tilting the board turns the gaze, shaking it hard four times makes the eyes dizzy (QMI8658). Adapted from [zongzhu-bot](https://github.com/Liu-zhongxian/zongzhu-bot) (MIT).
- **A clean main screen.** The status icons, status text, speaker button and button hints are hidden; a touch fades them in, 4 seconds later they fade out, and while hidden they cannot be pressed.
- **Waiting ring.** Timing starts when you release the button and the ring around the screen fills in 60 seconds; the device returns to the "thinking" state while waiting, and the ring resets when the answer starts to be spoken.
- **Away from home (joined to another Wi-Fi).** The address is chosen by Wi-Fi name (`MUSE_HOME_SSID`); the device does not wait for Muse, and the request carries `away` so the gateway answers directly; Muse's background reconnects (the VM session, token refresh, the Noise session, the chat session) pause.
- **Two read/write fixes.** (1) ESP-IDF's `esp_http_client_read` waits until its buffer is full, so a short acknowledgement followed by a long silence got stuck; the firmware now reads one byte at a time. (2) When the gateway deliberately answers 503 (telling the device to ask Muse), that is no longer treated as a failure and retried on the fallback address (it wasted about 2 seconds every turn).

## The gateway and the home side

- **Language models.** Besides Alibaba, Volcano Engine, DeepSeek and Custom, a "Responses API" provider (compatible with OpenAI's Responses, and able to carry `web_search`) was added. With a subscription account through [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI), Gemini in "Custom" with `{"tools":[{"google_search":{}}]}` answered correctly in 2 to 3 seconds; GPT through the Responses API took about 17 seconds because it searches before it writes. This uses a subscription account as an API through an unofficial proxy, which may violate the terms of service; weigh that yourself.
- **System prompt.** It carries today's date and asks the model to search first for "this year" and "the latest"; `* # \`` in replies are removed.
- **Public entrance.** The router forwards a port to an HTTPS forwarder (`gw-proxy.mjs` in the author's own home setup, which is not part of this repository: rate-limited, blocks wrong tokens, logs timings) that lets through only `POST /chat /tts /stt /bot-reply`; the certificate comes from acme.sh with DNS validation. Providers usually block 80 and 443, which is why DNS validation and a high port are used.
- **Webhook bot** (the Grok Bot, for example). When away, every turn goes to it; the device is first made to say an acknowledgement, then the Webhook is sent, and the bot `POST`s its answer back to `/bot-reply/<id>/<token>` (a one-time token, in the path to avoid `&amp;` escaping); if the Webhook cannot be sent, the ordinary language model answers in the same reply. Optionally through a relay server with a public IP (an SSH reverse tunnel plus nginx, also part of the author's home setup, not included here): the callback uses the standard port 443, and if the tunnel is down it goes direct automatically.

|---|---|

## Traps I fell into

- An nginx reverse proxy speaks HTTP/1.0 by default, and some bots' servers answer `426 Upgrade Required`; add `proxy_http_version 1.1`.
- The Webhook path is a secret, so turn off the access log on the relay site.
- Editing a log file with `sed -i` makes nginx keep writing to the deleted old file; use `nginx -s reopen`.
- The forwarder's allow-list must include the path the bot calls back on, or the callback is refused with 404.

## 2026-10-21: the WireGuard tunnel and a changeable avatar

See the two items in the README's firmware section (now [FIRMWARE.md](FIRMWARE.md)). In short: the tunnel uses `esphome/wireguard`, and ESP-IDF 6.0.1 has three traps, all handled in the patch:

- The `esp_netif` callback takes the `state` of an lwIP network interface for its own pointer, so adding the tunnel interface crashed (`LoadProhibited`). `CONFIG_ESP_NETIF_BRIDGE_EN=y` must be on, so that esp_netif keeps its pointer in the client data. (Now the firmware requires this option itself.)
- The component allows only one address per peer by default, so `0.0.0.0/0` could not be added and packets were dropped with "no peer". The patch defines `CONFIG_WIREGUARD_MAX_SRC_IPS=2` for it in `components/muse/CMakeLists.txt`.
- A router's DNS may return fake addresses (measured here: `198.19.0.x`), which do not work inside the tunnel, so once the tunnel is up it uses a public DNS through the tunnel and clears lwIP's DNS cache.

Also: the component calls lwIP's raw interface and must hold `LOCK_TCPIP_CORE()`; the handshake needs the system clock, so NTP is used first if the clock was never set.

### Same day, an addition: the Answers menu and memory

- Settings → Answers chooses who answers (Muse / Grok Bot / the model), at home and away; WireGuard's Auto starts the tunnel only when Muse is chosen. `POST /chat` takes a new field `gemini: true`.
- Requests to the gateway (recognition, chat, speech) are bound to the Wi-Fi interface with `esp_http_client_config_t.if_name` and do not enter the tunnel; the connection to Muse is not bound.
- Internal RAM is tight: the stacks of the per-turn network tasks (recognition, chat, fetching speech) and of the WireGuard manager task are put in PSRAM with `xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)` and ended with `vTaskDeleteWithCaps(NULL)`; nothing in those tasks may write to flash. Without this, a long reply with Muse chosen stopped at the dozenth piece of speech because fetching speech failed.
